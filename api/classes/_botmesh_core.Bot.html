    Class Bot

    The bot engine. Register handlers, flows, conversations, hooks and plugins, then call start(). A bot drives exactly one transport (BotConfig.provider); everything it receives and sends goes through the neutral IProvider contract, so the same code runs on WhatsApp, Telegram or any other channel.

    Example

    import { Bot, flow } from '@botmesh/core'
    import { BaileysProvider } from '@botmesh/baileys'

    const bot = new Bot({ provider: new BaileysProvider({ session: 'my-bot' }) })

    bot.when('hi', (ctx) => ctx.reply('Hello! 👋'))
    bot.use(
      flow('register')
        .ask('What is your name?', 'name')
        .say((_ctx, c) => `Nice to meet you, ${c.state.name}!`),
    )

    await bot.start()

    on

    • on<K extends keyof BotEvents>(
          event: K,
          listener: (...args: BotEventArgs<K>) => void,
      ): this

      Adds the listener function to the end of the listeners array for the event named eventName. No checks are made to see if the listener has already been added. Multiple calls passing the same combination of eventName and listener will result in the listener being added, and called, multiple times.

      server.on('connection', (stream) => {
        console.log('someone connected!');
      });

      Returns a reference to the EventEmitter, so that calls can be chained.

      By default, event listeners are invoked in the order they are added. The emitter.prependListener() method can be used as an alternative to add the event listener to the beginning of the listeners array.

      import { EventEmitter } from 'node:events';
      const myEE = new EventEmitter();
      myEE.on('foo', () => console.log('a'));
      myEE.prependListener('foo', () => console.log('b'));
      myEE.emit('foo');
      // Prints:
      //   b
      //   a

    emit

    • emit<K extends keyof BotEvents>(event: K, ...args: BotEventArgs<K>): boolean

      Synchronously calls each of the listeners registered for the event named eventName, in the order they were registered, passing the supplied arguments to each.

      Returns true if the event had listeners, false otherwise.

      import { EventEmitter } from 'node:events';
      const myEmitter = new EventEmitter();

      // First listener
      myEmitter.on('event', function firstListener() {
        console.log('Helloooo! first listener');
      });
      // Second listener
      myEmitter.on('event', function secondListener(arg1, arg2) {
        console.log(`event with parameters ${arg1}, ${arg2} in second listener`);
      });
      // Third listener
      myEmitter.on('event', function thirdListener(...args) {
        const parameters = args.join(', ');
        console.log(`event with parameters ${parameters} in third listener`);
      });

      console.log(myEmitter.listeners('event'));

      myEmitter.emit('event', 1, 2, 3, 4, 5);

      // Prints:
      // [
      //   [Function: firstListener],
      //   [Function: secondListener],
      //   [Function: thirdListener]
      // ]
      // Helloooo! first listener
      // event with parameters 1, 2 in second listener
      // event with parameters 1, 2, 3, 4, 5 in third listener

          chatId: string,
          content: string | OutboundContent,

    broadcast

    • broadcast(
          chatIds: readonly string[],
          content: string | OutboundContent,
          opts?: BroadcastOptions,
      ): Promise<BroadcastResult>

      Send content (a string is sent as text) to many chats: in batches of batchSize (default 10) with concurrency parallel sends (default 1), pausing delayBetween between batches. A RateLimitedError pauses the whole broadcast for its retryAfterMs and retries that chat (up to retries times after the first send, default 3); other errors are recorded and the broadcast goes on. Abort signal to stop early — never-attempted chats come back in pending. bot.stop() cancels it the same way (with drain, stop waits for its in-flight sends), and a broadcast started on a bot that is not started (never started, or stopped) sends nothing. Duplicate ids are sent once. Each send takes the normal outbound path (send hooks, ledger, the provider's rate limiter) but not the dispatcher's per-chat queues, so inbound handling is never blocked; still, launch it with void (not await) from inside a handler so that chat's queue is not held.

      Parameters

      • chatIds: readonly string[]
      • content: string | OutboundContent
      • Optionalopts: BroadcastOptions

      Returns Promise<BroadcastResult>

      Example

      const ac = new AbortController()
      const res = await bot.broadcast(chatIds, '🎉 Nueva promo!', {
        batchSize: 10, delayBetween: '2s', signal: ac.signal,
        onProgress: (done, total) => bot.logger.info(`${done}/${total}`),
        onFail: (chatId, error) => bot.logger.warn({ chatId, err: error }, 'broadcast failed'),
      })
      // → { total: 500, sent: 480, failed: 20, skipped: 0, errors: [{ chatId, error }], messages, cancelled: false, pending: [] }

    trigger

    • trigger(name: string, opts: TriggerOptions): Promise<TriggerResult>

      Start a registered flow/conversation for a subject without waiting for them to write — reminders from bot.schedule(), webhooks, admin panels. data seeds c.state. The start goes through the same gates as a message (blacklist / whitelist, human handoff) and the chat's FIFO queue; by default a subject that already has a live or dormant conversation is left alone (ifActive: 'replace' cancels it). Resolves once the conversation is entered — not when it ends (listen to 'conversation:ended' for that). Rejects when name is not registered. Safe to await from a handler or command of the same chat: the trigger then runs inline in that message's queue slot instead of queuing behind it (which would deadlock the chat). Awaiting a trigger for a DIFFERENT chat whose handlers in turn await a trigger back into this one can still deadlock — launch those with void. Before-message hooks, matchers and the 'message' event do not run, and nothing is persisted for the synthetic inbound (ctx.raw is { synthetic: 'trigger', name }).

      Parameters

      • name: string
      • opts: TriggerOptions

      Returns Promise<TriggerResult>

      Example

      bot.schedule('0 9 * * *', async () => {
        for (const cita of await db.citasDeHoy()) {
          await bot.trigger('recordatorio', { chatId: cita.chatId, data: { hora: cita.hora } })
        }
      })

    handoff

    • handoff(chatId: string, opts?: HandoffOptions): Promise<boolean>

      Hand chatId over to a human agent. Until resume, the Dispatcher skips every routing stage for that chat (commands, conversations, dormant resume, matchers, catch-all) except BotConfig.handoff.allowCommands; inbound messages are still persisted, hooks still run and the 'message' event still fires. Active conversations in the chat are cancelled silently and its dormant checkpoints dropped. Emits 'handoff' and persists the state on StoredChat.handoff (survives restarts with a persistent store).

      The state flips synchronously, so not awaiting is safe. Resolves true if the chat was not already handed off; never rejects for store failures (they go to the 'error' event). Throws TypeError synchronously on an empty chat id.

      Parameters

      • chatId: string
      • Optionalopts: HandoffOptions

      Returns Promise<boolean>

    enterConversation

    • enterConversation(
          handler: ConversationHandler,
          ctx: MessageContext,
      ): Promise<void>

      Enter an inline ConversationHandler for the chat (or group participant) of ctx. To start a REGISTERED conversation or flow, use trigger (the by-name form here is deprecated).

      Fire-and-forget by design: it returns immediately, so a handler can start a conversation and return, releasing the chat's FIFO queue for the user's next message (which the conversation then receives). Any conversation already active on that key is replaced. Failures (e.g. an unknown name) are reported through the 'error' event, never as an unhandled rejection.

      The returned promise settles (it never rejects) once the conversation has ended and released its key. Never await it inside a handler: that blocks the chat's queue, so the user's answer could never reach the conversation.

      Parameters

      • handler: ConversationHandler
      • ctx: MessageContext

      Returns Promise<void>

      Example

      bot.when('pedido', async (ctx) => {
        bot.enterConversation(async (c) => {
          const ok = await c.ask('¿Confirmas? (sí/no)')
          await c.say(ok === 'sí' ? 'Hecho' : 'Cancelado')
        }, ctx)
      })

    plug

    • plug<TConfig = Record<string, unknown>>(
          plugin: Plugin<TConfig>,
          config?: TConfig,
      ): () => void

      Install a plugin (optionally with config). Unlike use, returns an unsubscriber (not the bot: do not chain) that first calls the plugin's uninstall() and then removes, newest first, what it registered through ctx.bot: commands, matchers, conversations/flow triggers, hooks, nested plugins, runtime flows and onDispose callbacks. Calling it again is a no-op. It does NOT undo event listeners (on/once), provide()d tools, locale() messages, schedule/every/delay jobs, onIdle handlers or a flow replaceFlow() overwrote: undo those in ctx.onDispose() (e.g. ctx.bot.unprovide(name)).

      install() should be synchronous. If it throws, whatever it registered so far is rolled back and the error is rethrown; if it returns a promise that rejects, the rejection goes to the 'error' event instead of crashing the process.

      spec.requires lists plugin names that must already be plugged (a nested plugin may require its parent); a missing one throws before install() runs. Flows registered through ctx.bot.registerFlow() (or created by ctx.bot.replaceFlow()) are unregistered on unplug.

      One instance per plugin name: plugging a name that is already plugged throws (unplug the first instance before plugging it again), unless every instance sets spec.multiple: true.

      config is typed by the plugin (definePlugin<MyConfig>()), so an unknown option or a wrong type is a compile error.

    onIdle

    • onIdle(duration: string | number, handler: IdleHandler): () => void

      Run handler once when a chat stays quiet for duration ('10m', '1h', '1d', ms…) after its last processed inbound message. Every new inbound message from that chat reschedules it, and re-arms it after it fired. ctx is that last message's context, so ctx.reply('¿Sigues ahí?') answers in the right chat. Handler errors go to the bot 'error' event. Pending timers are cancelled by clearIdle, by the returned unsubscribe and by stop(). The handler never runs for a chat in human handoff: a 'handoff' event carrying { chatId } cancels that chat's timers, and its messages do not re-arm them until a 'resume' event for that chat (the bot's own isHandedOff() state is honoured too, when present). duration must be positive and at most 2^31 − 1 ms (about 24.8 days, the longest a Node timer can wait); otherwise it throws RangeError.
