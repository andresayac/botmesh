# @botmesh/core

## 2.0.0-beta.4

### Minor Changes

- 8d86135: Close three gaps found while writing the docs examples:
  
  - `c.ask()` and `c.waitText()` accept a native button or list tap that carries text (`type: 'buttons' | 'list'` with a non-empty body: the button id or selected title, the same value `c.choose()` reads) as the answer, instead of re-prompting as if the user had sent media. Taps without text and media still re-prompt.
  - `createTestBot()` from `@botmesh/core/testing` also takes a `defineBot` factory: `await createTestBot(createBot, options?)` calls it with the `MockProvider` (or its chaos wrapper) and starts the bot it returns. It throws a `TypeError` when the factory does not return a bot built on that provider.
  - New `bot.unprovide(name)`, the inverse of `bot.provide()` (which still returns the bot for chaining): it removes the injected tool and returns whether one existed. Plugins call it from `ctx.onDispose()`.
- 7e9c369: `@botmesh/core/spi` exports the two flow-interpreter hooks the core interpreter uses, now under semver: `pauseControls(controls, ms)` (a pause that ends early when the conversation is aborted, replaced or the bot stops, then throws if the conversation is gone) and `runFormStep(form, ctx, c, opts?, flowTimeoutMs?)` (runs a native or degraded form and stores its answers). Code that runs declarative steps inside a `do`, such as `@botmesh/flow-schema`, imports them from the SPI instead of `@botmesh/core/internal`. They stay available from `/internal` as well.

### Patch Changes

- 618502b: `bot.plug(plugin, config)` types `config` with the plugin's own config type (`definePlugin<MyConfig>()`). A config declared with an interface (such as `NluPluginConfig`) is accepted as is, where it failed before with "Index signature for type 'string' is missing", and an unknown or mistyped option is now a compile error instead of passing silently.
- c361ba3: `ChaosProvider` and `RecordingProvider` (`@botmesh/core/testing`) implement `IProvider` again under `exactOptionalPropertyTypes` with `skipLibCheck: false`: their optional delegated members (`ingest`, `downloadMedia`, `typing`…) were typed `X | undefined`, which broke the consumer's build with TS2420 inside the published `.d.ts`.

## 2.0.0-beta.3

### Major Changes

- 0c0d203: **Breaking (2.0 stable behaviour decisions).** See the "Migrating to 2.0" guide (`docs/guide/migration-2.md`).
  
  - **Built-in texts default to English.** The default locale is `'en'` (timeouts, "too many attempts", wait prompts, slash-command replies, form hints; the form skip word is `skip`). The Spanish texts are still bundled: the new `BotConfig.lang: 'es'` restores them without turning on per-user language resolution. `lang` and `i18n.defaultLocale` must agree when both are set.
  - **`retries` always counts attempts after the first.** New `maxAttempts` (total answers, first included; default 3 as before) on waits (`ask`, `waitText`, `choose`, …) and `flow().form()`. `retries: N` now means `maxAttempts: N + 1` (during the alphas it meant N in total): rename `retries: N` to `maxAttempts: N` to keep the old budget. Conflicting or invalid values throw a `TypeError` (in flows, when the flow is defined). `bot.broadcast()` takes `retries` (same meaning; `maxRetries` is a deprecated alias).
  - **Sends need a running bot.** Sends, edits and stream updates before `bot.start()` (or after a failed start) and after `bot.stop()` reject with the new `BotNotRunningError` (`code: 'BOT_NOT_RUNNING'`) and never reach the provider. Sends are accepted from the moment the transport starts connecting, so a `'ready'` listener can send. Concurrent `start()`/`stop()` calls run one at a time in call order.
  - **Rate-limited `ctx` sends retry once.** A `ctx` send rejected with a `RateLimitedError` asking for at most 5 s is retried once (it was twice); `BotConfig.rateLimitRetry: { retries, maxWaitMs } | false` configures it.
  - **Flows fail when they are defined:** `.choose(prompt, {})`, non-object options, an option without a label and an empty state key in `.ask()`/`.choose()` throw a `TypeError`.
  - **Invalid provider events** (not an object, unknown `kind`, a message without `chatId`/`ref`/`senderId`/`type`/`body`, …) are dropped and reported once on `'error'` as the new `InvalidProviderEventError`, instead of a generic `TypeError`.
  - **A before-hook calling `next()` twice** keeps the first dispatch (later calls return the same promise) and the misuse is reported on `'error'`; the message used to be dropped. `HookSystem` takes `{ report }`.
  - **Ids in logs are hashed.** The bot's own log lines carry chat/sender ids through the new `BotConfig.logIds` (`'hash'` default, the same HMAC as trace spans; `'raw'`, `'omit'`).
  - **`MemoryCoordinationHub`** evicts idle chats beyond `maxIdleKeys` (default 10,000); fences stay monotonic and a re-created chat reports `previousHolder: null`. New `hub.size` / `hub.maxIdleKeys`.
  - **File journals:** a corrupt line in the middle of the append log is refused on open with `code: 'APPEND_LOG_CORRUPT'` instead of silently dropping the later entries. New `FileDurability.open(path, { fsync: true })` flushes each snapshot before the rename (and defaults `appendLog.fsync`).

### Minor Changes

- ac11ddf: One rule for unsupported operations, and bounded waits.
  
  **Breaking:** an operation the transport cannot perform is now absent (the optional `IProvider` method is not defined and its capability flag is `false`) instead of a silent no-op:
  
  - `@botmesh/meta`: `CloudAPIProvider#typing()` and `#deleteMessage()` are removed (they did nothing).
  - `@botmesh/telegram`: `TelegramProvider#markRead()` is removed (bots get no read receipts; it did nothing).
  - `@botmesh/core/testing`: `MockProvider` reports `capabilities.typing` / `readReceipts` as `true` only when a `typing()` / `markRead()` method exists (a subclass or a test that adds one gets the flag; assigning the flag still overrides it). Before, both were `true` with no method behind them, which every `ctx` helper already treated as unsupported.
  
  `ctx.typing()`, `ctx.markRead()` and `ctx.delete()` stay no-ops on those channels. New `checkCapabilityContract` / `assertCapabilityContract` (and `CapabilityContractError`) in `@botmesh/core/testing` check that a provider's capability flags agree with its methods and that its text limits are valid.
  
  Also:
  
  - `RateLimitedError.retryAfterMs` is capped at 24 h, so no wait built on it overflows `setTimeout` (which fires at once past ~24.8 days).
  - `@botmesh/telegram`: a 429 `retry_after` is clamped (missing/invalid → 1 s, at most 24 h); a huge value used to make the poll loop spin.
  - `@botmesh/meta`: a local media path that cannot be read rejects with `UnsupportedContentError` (the fs error as `cause`) instead of a raw `ENOENT`.
- ac11ddf: `timestamp` is epoch milliseconds on every channel.
  
  **Breaking:** `InboundMessage.timestamp`, `InboundInteraction.timestamp`, `DeliveryStatus.timestamp` and `ctx.timestamp` are epoch **milliseconds** everywhere. `@botmesh/baileys`, `@botmesh/meta` and `MockProvider` (`@botmesh/core/testing`) used to emit epoch seconds; drop any `* 1000` in your code (`new Date(ctx.timestamp)` is now right).
  
  - A missing or invalid transport time is the receive time (`Date.now()`), never `0` (Baileys and the Cloud API emitted `0`).
  - `@botmesh/telegram`: a callback query (button press) carries the receive time; the Bot API sends no press time and the date of the message holding the keyboard could be days old.
  - `@botmesh/core` still converts a value below `1e12` from a third-party provider that emits seconds, for `ctx.timestamp` and the message log (soft path), and the message log keeps the receive time for a second-precision stamp of the current second whether it arrives in seconds or ms.
  - New contract helpers in `@botmesh/core/testing`: `checkInboundContract` / `assertInboundContract` (and `InboundContractError`) check epoch-ms timestamps, `respondBy`, `body`, `mentions` and the message type of a provider's events.
- ac11ddf: Long text is split into several messages automatically.
  
  **Breaking (behaviour):** a `text` send longer than the provider's `capabilities.maxTextLength` (UTF-16 code units) or the new `capabilities.maxTextBytes` (UTF-8 bytes) is no longer passed to the provider whole (which rejected it with `PayloadTooLargeError` on Telegram, Discord, Messenger and Instagram): the core sends it as several messages, in order. Set `new Bot({ splitLongText: false })` to keep the old behaviour.
  
  - Cuts land on the most natural boundary that fits (paragraph, line, sentence, word) and never inside a grapheme (surrogate pairs, ZWJ emoji sequences, flags, skin tones) or the chat's markup: links and URLs stay whole; a fenced code block, inline code, an emphasis run or an HTML element longer than the limit is closed at the end of a part and reopened at the start of the next (the fence keeps its language).
  - `before('send')` hooks run once on the whole text, and what they return is split: a footer or a translation applies to the whole message and every part still fits (a hook that makes a short text too long gets it split too, its explicit key suffixed from `#1`); an `abort()` skips the whole text. Each part is then a send of its own: `after('send')` hooks, the message log and the durable outbox see each part. Only the first part keeps `options.quoted`; an explicit `idempotencyKey` gets a `#2`, `#3`… suffix from the second part on. A failing part rejects the send and the rest is not sent.
  - Durability: when the outbox defers a part (`SendDeferredError`), the parts after it are journaled behind it, so the sweeper delivers every part, in order. `bot.enqueue()` splits too, into one record per part (`key`, `key#2`, …).
  - The splitter runs in linear time: the markup of a text is scanned once, with no pattern that rescans to the end of the line for an unclosed `_`, `*`, `[` or tag.
  - `SendResult` / `SentMessage` gain `parts?: MessageRef[]` (every part, in order; `ref` is the last one).
  - New `ProviderCapabilities.maxTextBytes`; `MockProvider` takes a `maxTextBytes` option. `ctx.stream()` honours it too.
  - `splitMessage(text, limit)` and `findSplitPoint(text, limit)` accept `{ maxLength?, maxBytes?, format? }` (new exported type `SplitTextOptions`) as well as a plain length.
  - `@botmesh/meta`: the Cloud API provider declares `maxTextLength: 4096` (its `text.body` limit), so longer text is split instead of failing at Graph.
- 088c920: Interactions on transports with `capabilities.interactionsRequireAck` (Discord) are now acknowledged by the core, as the `IProvider` contract always said: exactly one ack per interaction, the one from `ctx.acknowledge(text)` when the handler asks first, otherwise a deferred ack (`{ defer: true }`) before the context's first send, 500 ms before `respondBy`, or when routing ends. A later `ctx.acknowledge(text)` sends `text` as a normal reply. Interactions past their deadline (replays) are not acked, and a failing automatic ack is logged without blocking the reply. Transports without the capability are unchanged. `MockProvider` gains the `interactionsRequireAck` option and `interaction(data, { respondBy })`.
- 50fb2b6: `.persistent()` flows now checkpoint when they start (step 0) as well as after every step: a restart while the first `.ask()` waits resumes the flow there and asks again (it used to be lost unless durability or coordination was on). One more checkpoint write per flow entry.
- 50fb2b6: **Breaking (behaviour):** one policy for presence hints while the transport is disconnected. `ctx.typing()`, `ctx.recording()`, `ctx.markRead()` and the automatic typing indicator are best-effort: while the provider's last connection state is not `'ready'`, or once the bot is stopped, the bot does not call the provider; the hint resolves, is logged at debug and counted in the new `metrics().presenceSkipped` (`{ typing, markRead }`, `botmesh_presence_skipped_total{kind}` in `toPrometheus()`). The rule is part of the `IProvider` contract ("PRESENCE WHILE DISCONNECTED"); Baileys, the Cloud API and Telegram (and the other built-in channels) follow it when called directly too: `markRead()` / `typing()` resolve without contacting the transport while not connected. New `checkPresenceWhileDisconnected` / `assertPresenceWhileDisconnected` in `@botmesh/core/testing`.
- 50fb2b6: Stable-readiness leftovers:
  
  - **Breaking (messages):** the default messages of `OutsideSessionWindowError` and `RecipientUnreachableError` no longer include the chat id (it ended up in logs); it stays on `error.chatId`.
  - `ChaosProvider.selfId` and `RecordingProvider.selfId` (`@botmesh/core/testing`) return `null` instead of `undefined`, so they implement `IProvider` under `exactOptionalPropertyTypes` (TS2420).
  - `ctx.delete()` before `start()` or after `stop()` rejects with `BotNotRunningError` (`operation: 'delete'`).
  - `IMessageContext.acknowledge` is typed as a required method (it always existed at runtime).
  - A provider event whose `kind` is an unknown string is ignored (debug log) for forward compatibility; a non-string `kind` is still an `InvalidProviderEventError`.
  - `lang` and `i18n.defaultLocale` may name the same language with different precision (`'es'` / `'es-MX'`, the more specific one wins).
  - With `telemetry.ids: 'raw'` and no `logIds`, log lines keep hashing ids.
  - The TypeDoc reference documents `@botmesh/core`, `@botmesh/core/spi` and `@botmesh/core/testing`.
- 50fb2b6: New `'stopping'` bot event: `bot.stop()` on a running bot emits it right after inbound is closed, before the drain and the transport stop (`'stopped'` still comes last; a throwing listener goes to `'error'`). `@botmesh/ai` now aborts its in-flight model calls on `'stopping'` instead of `'stopped'`, so nothing waits on the model while the transport is stopping.

### Patch Changes

- 50fb2b6: Durable outbox and long text: a later part of a split text (`key#2`, `key#3`…) no longer overtakes an earlier part that is waiting for a retry (it waits behind it, and is dead-lettered with it), and the sweeper splits a journaled record whose text is over the channel's limit with the same splitter (first part under the record's key, the rest journaled first as `key#2`…; deterministic keys, so a retry or a second pass sends nothing twice). Waiting behind an earlier part does not use up a part's `outbox.retries` (`OutboxJournal.markFailed` takes `refund: true` to give the claimed attempt back), and parts are linked by the new `OutboxRecord.previousPart` field instead of their key, so your own idempotency keys ending in `#<n>` are never held back or dead-lettered with another send.
- 473728a: An empty or blank text trigger (`bot.when('')`, `'   '`, `['hola', '']`, `{ pattern: '' }`, `flow('')`, a conversation `trigger: ''`) throws a `TypeError` when it is registered. It used to match every message without text (a photo without caption), or every message with `contains`/`startsWith`/`endsWith`. `[]` is still accepted (it never matches; the usual trigger of a flow entered only by `goto()`). Use `IMAGE`/`MEDIA` for media and `bot.onMessage()` for a catch-all.
- b4c298d: `@botmesh/core/internal` exports `pauseControls(controls, ms)`, the cancellable pause the step interpreter uses: it ends early when the conversation is aborted, replaced or the bot stops, then throws if the conversation is gone. It is internal-only (not re-exported by the main entry, no semver guarantee); `@botmesh/flow-schema` uses it so nested `delay` steps no longer keep a timer alive after `bot.stop()`.
- c03fb3c: Cron expressions that can never fire are rejected when the task is created, as the scheduler guide promised: a value out of its field's range (minute `60`, hour `24`, day `0`/`32`, month `13`, weekday `8`), a step of `0`, an inverted range (`5-1`) or a day no selected month has (`0 0 30 2 *`) now throw a `TypeError` naming the field, instead of creating a task that silently never runs. Without a time zone the next-run search now reaches four years ahead like the zoned one (a `0 0 29 2 *` task registered more than a year before the next leap day used to never run) and skips non-matching days whole, so a far yearly slot no longer blocks the event loop for tens of milliseconds.
- a448242: Durability hardening. `FileDurability.open()` refuses a journal it cannot read back (an empty or truncated snapshot, malformed rows, a damaged append-log entry) with an error that names the file and says how to recover, instead of a bare `SyntaxError`/`TypeError` or a half-applied journal; `MemoryKv.restore()` validates every row. The append-only log is read in linear time (it re-measured the whole prefix for every line, so a long log took seconds or minutes to open). `durability.inbox.leaseMs` / `outbox.leaseMs` below 20 ms are rejected with a `ConfigValidationError`: they were clamped silently, the heartbeat could not keep them, and a message handled fine ended dead-lettered.
- a7992c3: Durable scheduler: a slot that fell due while the previous occurrence was still running (a handler slower than the interval, or an occurrence claimed late after a fail-over) was silently dropped, even with `missed: 'catch-up'` or `'run-once'`. Under those policies it is now claimed next and goes through the policy (run normally within the grace period, otherwise as missed). `'skip'` is unchanged.
- 0864a3b: Durability with coordination: when another replica took a parked conversation, the reply to the waking message was keyed under the previous turn's causation, colliding with the outbox record of the question asked before the hand-over. With `durability.outbox.onDiverged: 'skip'` that reply was never sent (the user got no answer); with the default `'send'` it went out but counted a false `outboxDiverged` and logged a warning. The waking message now keys the sends that answer it, as on a live delivery.
- a998e70: Durability: the first sweep of a restarted replica (same `instanceId`) re-claimed its own `sending` outbox records to catch its dead incarnation's late writes, but it could also re-claim a send the NEW incarnation had just claimed while replaying a recovered message. That send's completion then carried a superseded fencing token: the message was delivered, but its outbox record stayed `sending` until the 60 s lease expired (seen as an intermittent timeout of the Redis Cluster crash matrix). The sweep now re-claims only own leases taken before `recover()` (`OutboxClaimOptions.reclaimOwnBefore`, honoured by every `DurableKv`-based journal); a journal that ignores the new option behaves as before.
- 473728a: `BotConfig.rateLimit` is deprecated: nothing in the core ever read it (pacing moved to the transports in v2). Setting it now logs a warning when the bot is constructed. Configure pacing on the provider (e.g. `new BaileysProvider({ rateLimit })`) and the retry of rate-limited replies with `BotConfig.rateLimitRetry`. The `DurabilityConfig.backend` TSDoc names the real backends (`new PostgresDurability(...)`, `new RedisDurability(...)`, `SQLiteStore#durability()`).
- 511589e: README: the Baileys pairing example uses `pairingPhoneNumber` (the new name of `pairingCode` in `@botmesh/baileys`).
- 9bb285a: Soft path for the new meaning of `retries`: the first time a wait, form or flow step sets `retries` without `maxAttempts`, the bot logs one warning (`logger.warn`, once per bot) saying that `retries: N` now allows N + 1 answers and that `maxAttempts` states the total. `MemoryCoordinationHub({ maxIdleKeys: 0 })` no longer evicts the chat it is about to use (every turn failed with `LeaseLostError('superseded')`); `0` now keeps only the most recent idle chat.
- 88c0fef: Fail fast on user mistakes that used to be silent, and keep errors in the logs:
  
  - The engine's own error logs (`dispatch error`, `conversation error`, `resume failed`, …) now pass the error pino-style (`{ err }` first), so a pino logger records the error and its stack instead of dropping it.
  - `new Bot({ provider })` names the mistake when `provider` is a class, a Promise or an object without `start`/`stop`/`send`/`onEvent` (it used to fail later with an unrelated store-namespace error).
  - Every send is checked after the `before('send')` hooks: a `text` that is not a string (`ctx.reply(undefined)`), media without a source, coordinates out of range, or a poll/buttons message with no options reject with a `TypeError` instead of reaching the transport. Every documented `MediaSource` is accepted, including the provider escape hatch `{ native }` (Telegram `file_id`, Cloud API media id).
  - A `ctx` reply (including a flow step's `say`/`ask`) that hits a `RateLimitedError` with a `retryAfterMs` of up to 5 s waits and retries it (at most twice) instead of ending the conversation with the generic error message. Longer waits and other errors surface as before; `bot.send()` is not retried (broadcasts keep their own back-off).
  - A trigger that is `undefined`/`null` throws when it is registered (it matched the literal text "undefined").
  - `bot.every()` rejects a zero, negative or non-finite interval (it spun on a 1 ms timer); `bot.delay()` rejects a negative or non-finite one; cron expressions with out-of-range values, reversed ranges or a zero step throw (they were accepted and never ran).
  - `flow().ask()`/`.choose()` reject `'__proto__'` as a state key (the answer was silently lost).
  - Test kit: `chat.expectReply()` no longer crashes on outbox entries without text.
- 59a09d1: `slashCommandsPlugin`: the built-in `/help` text lists `/cancel` (it was installed but not listed) and `/cancel` answers `✅ Conversación cancelada.` / `✅ Conversation cancelled.` instead of the `/reset` text. Override `core.commands.help` / `core.commands.cancel` with `bot.locale()` to keep custom wording.
- 473728a: `slashCommandsPlugin`: the built-in `/help` text lists `/start` (`/start, /help — this message`), which the plugin registers, and the plugin's `description` is in English.
- 2ff24f5: `bot.stop()` lets sends still in flight and the bookkeeping of sends the provider already accepted (after-send hooks and the outbound message-log row) finish, up to 5 s, before it closes the store, with or without `drain`. A reply sent right before `stop()` was missing from the message log and the store's "closed" error (e.g. `The client is closed` with `RedisStore`) reached the `'error'` event.
- a2c946a: `botmesh dev` accepts `--env-file-if-exists <path>`, the optional variant of `--env-file`: it loads the file when present and stays silent when it is missing, instead of exiting with an error.
- 5ad624e: The docs site is now published at https://andresayac.github.io/botmesh/. Each package's `homepage` points to its page there (the site root for `@botmesh/core`), and the README links to the guides open the site instead of the Markdown sources on GitHub (the `@botmesh/ai` README link to the side-effecting tools section also had a stale anchor).

## 2.0.0-alpha.2

### Minor Changes

- 2e16743: `@bot-wa/ai`: native tool / function calling. `aiPlugin({ tools })` maps each tool (description, JSON Schema or `safeParse` schema, handler, `confirm`) to Anthropic, OpenAI (and OpenAI-compatible presets), Gemini and Ollama, with a multi-step loop (`maxSteps`), per-tool timeouts, errors returned to the model, human confirmation for `confirm: true` tools through the conversation runtime (no FIFO deadlock) and audit events (`onToolEvent`, `bot.on('ai.tool')`). - 2232f88: Native form labels follow the user's language. `ctx.form()` / `flow().form()` fill a missing `cta`, `submitLabel` and (without `intro`/`title`) body from the new `core.form.cta`, `core.form.submit` and `core.form.body` catalog entries (`es`/`en`) in `ctx.lang`, through the exported `withFormDefaults()`. `@bot-wa/meta` no longer hard-codes Spanish: its fallbacks use the same catalog and `toFlowJson(def, { lang })` (also `publishForm(def, { flowJson: { lang } })`) picks the language of the published Flow's default submit label (default `'es'`, unchanged).
- 27620ef: Add a WhatsApp Cloud API 24 h customer-service window manager (`sessionWindow` option, `SessionWindowManager`, pluggable `SessionWindowStore`): reopen closed chats with an approved template and retry the original send when the user replies. Status events now carry the normalized `pricing`/`conversation` objects in `DeliveryStatus.platformData` (new optional field in core), and `provider.usage` aggregates per-chat/per-category usage and estimated cost. Window state is scoped per business number (`phoneNumberId`; shared managers via `forScope()`), and media is uploaded once before queueing so retries never re-read a drained stream or keep media bytes in memory.
- e4574e6: Tracing hooks, opt-in through `BotConfig.telemetry`. Without the key nothing changes (no span code runs). With a `BotTracer` (OpenTelemetry through the private `@bot-wa/otel`, or your own) the bot emits spans for inbound events, persistence, dispatch (queue wait, routing stage), handlers, conversation turns (one per stretch between waits; flow steps as events), triggers, broadcasts, pacing and sends, with chat/sender/message ids hashed by default (`ids: 'hash' | 'raw' | 'omit'`, `idKey`) and never message bodies, prompts or error messages (unless `errorMessages: true`). A throwing tracer never breaks the bot. New API: `bot.tracing`, the `BotTracer`/`BotTracing`/`BotSpan`/`TelemetryConfig` types, `TRACE_ATTR`, `SPAN_NAMES`, `noopTracer`, `NOOP_TRACING`, `errorTypeOf`, and `createRecordingTracer()` in `@bot-wa/core/testing`. `Dispatcher.conversationMatcher()` takes an optional `{ flow }`.
  
  `@bot-wa/ai`: `AIClientOptions.tracing` (aiPlugin passes `bot.tracing`) and `providerName`. Model calls become `chat {model}` spans with OpenTelemetry GenAI attributes (models, token usage, finish reason, purpose; a timeout is `error.type = timeout`), tool calls `execute_tool {name}` spans with their outcome, and RAG retrieval a `bot.ai.retrieve` span; no prompts, completions, arguments or results are recorded. `GenerateInput.onStreamEnd` also reports `usage` when the provider streams it (Anthropic, Gemini).
- b95b523: Opt-in runtime hardening: `BotConfig.echoFilter` drops inbound echoes of the bot's own sends (before access lists, dedupe and the journal; counted in `metrics().dropped.echo`); `IStore.setCheckpointIf`/`clearCheckpointIf` (optional CAS used with `coordination`, with `FlowCheckpoint.revision`) so a frozen replica cannot overwrite the new owner's checkpoint; `FileDurability.open(path, { appendLog })` appends deltas to `<path>.log` with periodic compaction instead of rewriting the snapshot.
- 5196990: Durable scheduler tasks (opt-in). `bot.schedule/every/delay(spec, { id, missed, maxCatchUp, leaseMs }, (run) => ...)` persists the next run in a `ScheduleStore` (`BotConfig.scheduler.store`, in memory by default), applies a missed-run policy (`skip`, `run-once` or `catch-up`) to slots no replica ran in time and claims each occurrence under a fenced lease so replicas never run it concurrently (at least once; `run.occurrenceKey` is an idempotency key). `bot.forgetTask(id)` deletes a stored schedule (orphans, one-shot tombstones); fencing tokens never go backwards for an id, even across deletes. Optional scheduler leadership (`scheduler.lease`, type `SchedulerLease`): a fenced `LeaseProvider` (`MemoryLeaseProvider`, new contract) or the multi-replica `Coordinator`, which a bot with `BotConfig.coordination` uses by default. `@bot-wa/sqlite-store` adds `SQLiteStore#schedules()` (and `SQLiteScheduleStore`, whose constructor takes a structural `SQLiteDatabaseLike`, so consumers need no `@types/better-sqlite3`); `@bot-wa/redis-store` adds `RedisStore#schedules()` and the fenced `RedisStore#leases()`. Tasks without `id` behave as before.
- 2c4f9f0: `messageKey(ref)` percent-escapes `%` and `:` in the chat id and the message id, so ids that contain `:` (Twilio's `whatsapp:+1…` chat ids) no longer collide; keys of ids without `:` or `%` are unchanged. New `legacyMessageKey(ref)` returns the old unescaped key. SQLite and Redis stores write the new key, still read and delete rows stored under the legacy key (checking the stored `ref` is the requested message, since a legacy key can be another message's new key), and drop the legacy copy when a message is saved again — no manual migration.
- efb1fa6: Native streaming of long/AI replies with `ctx.stream(source, opts)`. The strategy comes from the new `ProviderCapabilities.streaming` field (`'draft' | 'edit' | 'none'`): native drafts (Telegram `sendMessageDraft`, with `can_stop`/`keep_on_stop`), throttled message edits (Discord, Telegram groups) or sentence chunks with typing (WhatsApp). Updates are throttled, cancellation is supported (`signal`, the user's stop button) and no message exceeds `maxTextLength`. New exports: `streamText`, `resolveStreamStrategy`, `splitMessage`, `findSplitPoint` and their types; `IProvider.sendDraft`; `MockProvider({ streaming })`. `@bot-wa/ai` gains `AIClient.streamReplyInChat()` and the `stream` option for the autoresponder. The Telegram long-poll now also asks for `stopped_message_generation` updates. Live edits and drafts run the `before('send')` hooks (payload `stream: 'draft' | 'edit'`) and the message log keeps the final edited text; rate-limited edits back off for `retryAfterMs`; `onCancel: 'discard'` deletes the live message when the transport can. The streamed autoreply honours refusals (`refusalMessage`, not stored), replies `errorMessage` on an empty answer and, with `onCancel: 'discard'`, keeps a cancelled answer out of the context.
- 4fc0560: Add native forms: `flow().form(definition, opts)` collects typed fields (text, number, email, date, select, multiselect, opt-in) with validation. Providers with the new `capabilities.forms: 'native'` receive an `OutboundContent` of kind `'form'` and reply with `'form'` inbound messages (`formReplyBody()` / `parseFormReply()`); every other provider gets field-by-field questions. `describe()` draws `form` nodes and `lint()` checks their timeouts and `c.state` key collisions. `@bot-wa/meta` renders forms as static WhatsApp Flows (`toFlowJson`, `toFlowMessage`, `publishForm()`, `config.flows`) and turns `nfm_reply` webhooks into form replies. Other providers reject the `form` kind with `UnsupportedContentError`. The new optional `IProvider.canRenderForm(form, { nativeId })` (exposed as `ctx.canRenderForm()`) lets a native provider say it has no native form for a definition; `CloudAPIProvider` implements it, so a form without a mapped Flow is asked field by field without first sending (and failing) a form message. Ambiguous grouped numbers (`1.500`, `1,500`) are rejected instead of being read as 1.5.

### Patch Changes

- ddfb1e9: The blacklist/whitelist now run before inbound dedupe: a blocked message or interaction is no longer recorded as seen, so a redelivery after un-blocking is processed. While still blocked, every delivery counts in `metrics().dropped.blocked` (never `duplicate`).
- 588fa34: `ctx.typing()`, `ctx.recording()`, `ctx.replyWithTyping()` and the `ctx.stream()` indicator are best-effort: a rejecting or throwing `provider.typing()` is logged at debug and ignored, so a failing indicator never aborts the reply after it. The Bot's default logger (no `logger`, no `debug`) now logs at `warn` instead of `error`, so warnings from plugins and handlers (e.g. a failed AI autoreply) are visible without `debug: true`.
- 909fa96: `BotConfig.logger` now accepts any `LoggerLike`, not just pino: a pino-shaped logger passes through untouched and any other one (`console`, `{ debug, info, warn, error }`) is adapted (`child()` forwards or reuses the logger, `trace`/`fatal` are no-ops). Before, a `LoggerLike` without `child` compiled but threw in the `Bot` constructor. New internal seam `toBotLogger()` (`core/src/core/bot/logger.ts`).
- 31fcc2e: The `Bot` omits `undefined` fields from its chat and contact upserts, so a message without a display name (or chat name) no longer erases the one already stored. `IStore.upsertChat` / `upsertContact` document the contract: an own field set to `undefined` unsets it, so partial upserts must omit unknown fields.
- f8c1d4f: `FileDurability`: a second `open()` of the same file in the same process is refused (`already open in this process`) until the first journal is closed; before, the lock with our own pid was taken and the two instances overwrote each other's snapshots. A lock file with our pid and no open journal in this process (a restarted container reusing pids) and one of a dead process are still taken over. An empty or garbled lock younger than 10 s is no longer treated as stale: `open()` waits up to the new `lockWaitMs` option (default 2 s). `close()` is idempotent, waits for pending writes and makes later writes reject; new `locked` getter.
- 1a81406: `MemoryStore` documents its default cap of 1000 messages per chat (RAM only; the persistent stores stay unbounded unless configured), accepts `maxMessagesPerChat: Infinity` to disable it, and rejects a negative, fractional or `NaN` cap with a `RangeError`.
- 310db8d: `MockProvider.editMessage` / `deleteMessage` / `sendDraft` are real class methods again, so a subclass that defines them as methods typechecks (no TS2425). The new `supports: { edit, delete, drafts }` option chooses which ones are exposed (defaults follow `streaming`); a disabled one reads `undefined` on the instance so the bot treats it as unsupported, and an explicit `false` also hides a subclass override.
- 6ea4442: Provider events (`reaction`, `poll`, `group`, `presence`, `status`, `call`) follow the same hook contract as `message` and `send`: a `before` hook that aborts now suppresses the `after` hooks and the `bot.on(...)` event, which used to run anyway.
- 634993f: `bot.stop()` no longer leaves work or timers behind under load: `stop({ drain: true })` clears its deadline timer when the sends finish early, paced replies still waiting (`BotConfig.typing`, `{ delay }`) are woken and dropped at once, running `ctx.stream()`s are cancelled and send, edit or delete nothing more once the provider stops (new optional `StreamTarget.shutdown` signal), a message still queued for a chat is dropped instead of starting a conversation after the stop, and the conversation runtime no longer keeps a shutdown flag per aborted non-persistent conversation. `bot.deleteSubject()` also forgets the language the provider reported for the subject. New `ConversationRuntime.close()`/`open()`/`isClosed()` and `I18n.forget()`.
- 23371fb: Fix races and lifecycle edge cases: a matcher registered while a message is being routed no longer makes another matcher run twice; entering a conversation discards that key's dormant checkpoint (the stale flow used to resume on the next message); `start()` reloads dormant checkpoints from the store instead of merging them with the pre-`stop()` ones; `bot.deleteSubject()` cancels the subject's live and dormant conversations; a `stop()`/`start()` while a scheduled task runs no longer forks its timer chain or re-runs a `delay()` task; delivery receipts never move a message's status backwards (a `failed` after `delivered` still wins, and a receipt's error is always kept) and are written in order per message; the store clear of a replaced dormant checkpoint can no longer land after, and wipe, the new persistent flow's first checkpoint; the scheduler no longer fires runs more than ~24.8 days away in a tight loop (quarterly crons, `delay('40d')`), it waits in chunks within the `setTimeout` limit; `bot.broadcast()` before `start()` sends nothing. `bot.plug()`'s unplug now also removes conversations, flows and nested plugins registered through `ctx.bot` and calls `uninstall()` once; a throwing `install()` is rolled back and a rejected async one goes to the `'error'` event. Cron: stepped ranges (`1-5/2`) honour their upper bound, `7` means Sunday and a malformed expression throws a `TypeError` naming the field. `c.choose()` with no options throws a clear error. New `ConversationRuntime.abortWhere()`.
- ce7790f: Packaging: dependencies between `@bot-wa/*` packages are published as caret ranges (`^x.y.z`, from `workspace:^`) instead of exact versions, so npm dedupes a single `@bot-wa/core` instead of installing a second copy when one package lags a patch behind. Published READMEs use absolute GitHub links (relative links broke on npmjs.com), and `@bot-wa/core`/`@bot-wa/http` gain `repository.directory`, `homepage` and `bugs` metadata.
