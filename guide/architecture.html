On this page

Architecture ​

How @botmesh/core is put together: the package layers, the modules behind the Bot class, the path a message takes in and out, and where the opt-in features (durability, multi-replica coordination, the durable scheduler, tracing) plug in. You don't need any of this to write a bot. It is for people who extend the core, write a channel or store, or debug what happens between the provider and a handler.

Layers ​

The framework is a pnpm monorepo. Dependencies only point down:

LayerPackages
Engine@botmesh/core (its only runtime dependency is pino)
Shared infrastructure@botmesh/http (anti-SSRF client), @botmesh/graph-core (Meta Graph helpers), @botmesh/wa-gateway-kit (identity, REST and media shared by Evolution and WPPConnect), @botmesh/server (webhook ingress)
Channels@botmesh/baileys, @botmesh/meta, @botmesh/telegram, … (each implements IProvider)
Stores@botmesh/sqlite-store, @botmesh/redis-store, … (each implements IStore)
Plugins / product@botmesh/ai, nlu, manager, inbox, …

The core is transport-agnostic. It knows nothing about JIDs, QR codes or webhooks: chat, user and message ids are opaque strings it never parses, and the provider resolves identity aliases (LID/PN on WhatsApp, sender_chat on Telegram) before it emits an event, so the same person always arrives with the same senderId. Everything channel-specific lives in the channel package.

Inside the Bot ​

Bot is a thin facade: its methods carry the public documentation and delegate. The engine lives in packages/core/src/core/bot/:

ModuleResponsibility
compose.tsThe constructor body: config defaults, logger, store + namespace, every subsystem, in a fixed order; builds the kernel and the modules below
kernel.tsBotKernel, the shared internals (subsystems + lifecycle state) every module receives, plus tiny shared helpers
logger.tsAdapts BotConfig.logger (pino, console or any { debug, info, warn, error }) to the child()-capable logger the modules use
lifecycle.tsstart() / stop() as an ordered list of steps, with rollback and drain
inbound.tsThe provider's event stream → fromMe / echo filter → access gates → dedupe → persistence → groupMode → Dispatcher; calls and provider events (reactions, receipts…)
outbound.tsSends and edits through the send hooks, the message ledger, paced replies, typing and ctx.stream()
presence.tsThe presence-while-disconnected policy: typing / markRead skipped (debug log + metrics().presenceSkipped) while the transport is not 'ready'
rateLimitRetry.tsThe short in-place retry of rate-limited ctx replies (BotConfig.rateLimitRetry)
contextFactory.tsBuilds the MessageContext (ctx) of a message, a projected call or a bot.trigger()
interactionAck.tsThe single automatic ack of an interaction on a transport with interactionsRequireAck (Discord): before the first send, near respondBy or when routing ends
gates.tsAccess lists and human handoff admission, with their drop counters and logs
handover.tscoordination.handover (only with coordination): records a flow step's answer in its checkpoint and rebuilds it on the replica that takes the chat
lang.tsctx.lang resolution and the Dispatcher's language seams
persistence.tsChat / contact / handoff writes, ordered per chat
events.tsThe error and observability event outlet
routes.tswhen, conversation, command, onMessage, onType, hooks
pluginHost.tsplug(): a scoped bot whose registrations are undone on unplug
ops.tstrigger, triggerFlow, broadcast, metrics, flow inventory, subject-data collaborators

Three rules keep this working:

  • No #private fields on Bot. A plugin receives Object.create(bot) as ctx.bot; its methods run with this set to that object, and a #private read through it would throw. The kernel is reached through this, so through the prototype.
  • Late-bound seams. Modules call the bot back through closures (bot.emit, bot.trigger, bot.isHandedOff…) read at call time, so a spy, a subclass override or a plugin-scoped override installed later is honoured.
  • Behaviour goes in a module, not in the facade. Each module stays under 500 lines and opens with a comment saying what it does and what it does not.

Inbound pipeline ​

Dashed boxes only exist when their feature is configured.

flowchart TD
    P["Provider event"] --> K{"message / interaction?"}
    K -->|"call"| CALL["Access + handoff gates → 'call' hooks + event → CALL triggers (dispatchEvent)"]
    K -->|"reaction, poll, group, presence, status"| HE["before/after hooks + bot event"]
    K -->|"yes"| FM{"fromMe / echo of a bot send?"}
    FM -->|"yes"| X0["Dropped (fromMe; echo: dropped.echo)"]
    FM -->|"no"| ACL{"Access lists"}
    ACL -->|"blocked"| X1["Dropped (dropped.blocked)"]
    ACL -->|"allowed"| DD{"Dedupe: chatId + id"}
    DD -->|"seen"| X2["Dropped (dropped.duplicate)"]
    DD -->|"new"| DUR["Durable inbox: journal the event"]
    DUR --> PER["Persist chat, contact, message"]
    PER --> GM{"groupMode"}
    GM -->|"ignored"| X3["Stops (still persisted)"]
    GM -->|"ok"| Q["Per-chat FIFO queue"]
    Q --> TURN["Cross-replica chat turn"]
    TURN --> D["Dispatcher: language → before('message') → handoff gate → command → active conversation → dormant resume → matchers → catch-all → after('message') + 'message' event"]
    style DUR stroke-dasharray: 5 5
    style TURN stroke-dasharray: 5 5

The routing stages inside the Dispatcher, in order, are described in Core concepts. Two entry points skip parts of this path: calls go through the same access and handoff gates and only reach CALL type triggers, and bot.trigger() goes through the access lists, then takes the chat's queue slot (runExclusive), the handoff gate and language resolution, and starts the conversation directly — no dedupe, persistence, message hooks or matchers.

Outbound pipeline ​

flowchart TD
    S["ctx.reply / bot.send / broadcast"] --> PACE["Pacer (ctx text replies): delay + typing"]
    PACE --> IDEM["Durable idempotency lookup"]
    IDEM -->|"already sent"| PRIOR["Answered from the outbox (no hooks, no provider call)"]
    IDEM -->|"new"| BS{"before('send') hooks"}
    BS -->|"abort()"| SK["skipped: true"]
    BS -->|"proceed"| FENCE["Replica fence: this replica holds the chat's turn / the session"]
    FENCE --> OB["Durable outbox: journal the send"]
    OB --> PS["provider.send"]
    PS -->|"ok"| AS["metrics → after('send') → message ledger (sent)"]
    PS -->|"deferred"| SW["Outbox sweeper delivers it later"]
    PS -->|"error"| FAIL["message ledger (failed) → error to the caller"]

    style IDEM stroke-dasharray: 5 5
    style FENCE stroke-dasharray: 5 5

ctx.edit() takes the same path with edit on the hook payload. The live previews of ctx.stream() (drafts and in-place edits) run only the before('send') hooks; the messages a stream finally sends take the full path. bot.enqueue() (durability only) runs the before('send') hooks, journals the send and returns at once; the outbox sweeper delivers it.

Lifecycle ​

flowchart LR
    subgraph start["start()"]
      direction LR
      A1["storage"] --> A2["coordination"] --> A3["restore conversations + handoffs"] --> A4["durability: recover"] --> A5["transport"] --> A6["jobs (scheduler)"]
    end
    style A2 stroke-dasharray: 5 5
    style A4 stroke-dasharray: 5 5

stop() closes inbound and cancels broadcasts, emits 'stopping' (plugins cancel long work there, e.g. @botmesh/ai aborts its model calls), stops or pauses the steps that produce new work (scheduler, durability sweeper), optionally drains in-flight sends (stop({ drain: true })), closes paced sends and aborts conversations (checkpoints are kept), then stops the remaining steps in reverse order (the storage step first lets sends still in flight and the ledger rows of sends the provider already accepted land, up to 5 s, before it closes the store). If start() fails, the steps already started are rolled back in reverse order and the error is rethrown.

An opt-in feature adds a lifecycle step; it does not scatter ifs through the start and stop code.

Where the opt-ins plug in ​

All of them are off by default. A bot that does not configure them runs exactly the code path described above without the dashed boxes.

FeatureConfigStages it touchesGuide
Durable processingdurabilityInbound: journals each event in an inbox before dispatch and acknowledges it once the work it started settled; replays it after a crash. Outbound: idempotency lookup and an outbox journal per send, with retries and a dead-letter queue. Lifecycle: a durability stepDurable processing
Multi-replica coordinationcoordinationInbound: each chat is processed under a cross-replica turn, in ingress order. Outbound: a fence refuses sends from a replica that lost its turn or the provider session. Lifecycle: a coordination step and leader election for exclusive transports. With coordination.handover, flow checkpoints carry the cut-short answer and non-persistent flows can be forwardedRunning N replicas
Durable schedulerschedulerJobs: tasks with an id are stored, survive restarts with a missed-run policy and run on one replica per occurrence (a lease)Scheduler
TracingtelemetryWraps the stages it observes in spans without changing their order or timing: provider event (bot.inbound), persistence, dispatch, handler, each conversation turn between waits, pacing and every send; @botmesh/ai adds model and tool spans. @botmesh/otel (outside the core, @opentelemetry/api as an optional peer) exports them. Each scheduled task run is a root bot.task span, and a conversation resumed on another replica (or after a restart) links its first turn to the turn that wrote the checkpoint (FlowCheckpoint.trace, W3C)Tracing
