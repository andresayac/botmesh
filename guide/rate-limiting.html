Rate Limiting (Anti-Ban) ​

WhatsApp bans accounts that send too many messages in a short period. The Baileys provider's built-in rate limiter protects your bot automatically — it's enabled by default and sits inside the provider's outbound send pipeline, so every ctx.reply(), bot.send(), bot.broadcast() and media send passes through it.

Transport-owned pacing

In v2 the pacing policy lives on the transport provider, not on the core: each transport may enforce its own limits (Telegram 429s, Discord buckets, Cloud API tiers — surfaced as typed RateLimitedErrors). This page covers the WhatsApp (Baileys) token-bucket limiter you configure when constructing BaileysProvider.

How it works ​

The limiter uses a token bucket algorithm with two independent buckets:

  • Per-chat — limits how fast you can send to a single conversation.
  • Global — limits your total outbound throughput across all chats.

When a bucket is empty, messages are queued (not dropped) and released as tokens refill; a throttled chat does not hold the others back. A send that waits in the queue longer than maxWait (30 s by default) rejects with RateLimiterTimeout, a RateLimitedError, so a caller never hangs. An optional jitter adds a random human-like delay between sends.

flowchart LR
    A["ctx.reply()"] --> B["before('send') hooks"]
    B --> C["RateLimiter.acquire(chatId)"]
    C -->|"tokens available"| D["provider.send()"]
    C -->|"bucket empty"| E["queue — wait for refill"]
    E --> D
    D --> F["after('send') hooks"]

Configuration ​

Pass rateLimit to the provider constructor (BotConfig.rateLimit is deprecated: the core ignores it and logs a warning):

ts
import { Bot } from '@botmesh/core'
import { BaileysProvider } from '@botmesh/baileys'

const bot = new Bot({
  provider: new BaileysProvider({
    session: 'my-bot',
    rateLimit: {
      perChat: { max: 5, window: '10s' },   // max 5 msgs per chat per 10s
      global:  { max: 50, window: '60s' },   // max 50 msgs total per 60s
      jitter:  { min: 500, max: 1500 },      // random 500–1500ms between sends
    },
  }),
})

perChat.windowstring | number'10s'Time window (e.g. '10s', '1m', 60000)
global.maxnumber50Max total messages in the window
global.windowstring | number'60s'Time window

Disable rate limiting ​

For tests or high-throughput trusted environments:

ts
const bot = new Bot({
  provider: new BaileysProvider({
    session: 'my-bot',
    rateLimit: { enabled: false },
  }),
})

New accounts are more sensitive

A freshly registered WhatsApp number gets banned faster than an aged one. Start conservative (3 / 10s per chat, 20 / 60s global) and increase gradually.

Programmatic access ​

The RateLimiter instance is internal, but you can import the class from the transport package for advanced use:

ts
import { RateLimiter } from '@botmesh/baileys'

const limiter = new RateLimiter({
  perChat: { max: 5, window: '10s' },
  global: { max: 50, window: '60s' },
})

await limiter.acquire('573001234567@s.whatsapp.net') // resolves when allowed
console.log(limiter.pending) // messages waiting in queue
limiter.reset() // clear buckets + reject queued sends

Short rate limits on ctx sends ​

Whatever the transport, a ctx send (reply, say, media, in handlers, flows and conversations) that the provider rejects with a RateLimitedError asking for a short wait is retried in place, so a conversation step does not end on a transient 429: by default once, when retryAfterMs is at most 5 s. BotConfig.rateLimitRetry tunes it (retries counts attempts after the first):

ts
new Bot({ provider, rateLimitRetry: { retries: 2, maxWaitMs: '10s' } })
new Bot({ provider, rateLimitRetry: false })   // never retry in place

A longer wait, other errors and bot.send() fail as before; bot.broadcast() (its retries option) and the durable outbox have their own back-off.

How it interacts with before('send') hooks ​

The rate limiter runs after before('send') hooks but before the actual provider send. If a hook aborts the send, the rate limiter is never consulted — aborted sends don't consume tokens.
