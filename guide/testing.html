Testing ​

@botmesh/core/testing lets you test a bot without WhatsApp, a phone or the network. It works with any test runner; the examples use Vitest.

ts
import { createTestBot, MockProvider } from '@botmesh/core/testing'

A first test ​

Keep your handlers and flows in a function that takes the bot, so the real bot and the tests register exactly the same thing:

ts
// src/flows.ts
import { flow, type Bot } from '@botmesh/core'

export function registerFlows(bot: Bot) {
  bot.use(flow('signup').ask('Your name?', 'name').say((_ctx, c) => `Welcome, ${c.state.name}!`))
}
ts
// tests/signup.test.ts   (pnpm add -D vitest, then: pnpm vitest run)
import { test } from 'vitest'
import { createTestBot } from '@botmesh/core/testing'
import { registerFlows } from '../src/flows.js'

test('signup asks for the name and greets', async () => {
  const { bot, chat } = await createTestBot()
  registerFlows(bot)

  await chat.send('signup')
  await chat.expectReply('Your name?')
  await chat.send('Ana')
  await chat.expectReply('Welcome, Ana!')

  await bot.stop()
})

expectReply rejects with a readable TestKitError when the reply does not arrive, so a failing test tells you what the bot sent instead.

createTestBot and MockProvider ​

ts
import { flow } from '@botmesh/core'
import { createTestBot } from '@botmesh/core/testing'

const { bot, provider, chat } = await createTestBot()
bot.use(flow('hi').ask('Your name?', 'name').say((_ctx, c) => `Hi ${c.state.name}`))

await chat.send('hi')
await chat.expectReply('Your name?')
await chat.send('Ana')
await chat.expectReply(/Hi Ana/)
await chat.expectNoReply()   // nothing else within 300 ms
chat.replies()        // every text/caption sent to this chat so far
provider.outbox       // every outbound message, any chat

createTestBot(config?) builds a started Bot on a MockProvider. To test the bot module you ship, pass its defineBot factory instead: await createTestBot(createBot) calls it with the MockProvider and starts the bot it returns (it throws if the factory built the bot on another provider). chat is one DM (user@s.whatsapp.net): its helpers simulate what the user does and assert on what the bot sent back. Every send*/press* helper yields one macrotask before resolving, so the dispatch has started.

HelperWhat it does
send(text, { type? })an inbound message (type defaults to 'text')
sendMedia(kind, bytes | { url, bytes? }, caption? | { caption, mimetype, filename, size })a media message: ctx.body is the caption and loadMediaOf(ctx) resolves with the bytes. { url } alone is metadata: the download rejects with MediaUnavailableError (the mock never touches the network)
sendLocation(location) / sendLocation(lat, lng, { name? })a shared location (ctx.sharedLocation, c.waitLocation())
sendReaction(emoji, target?)a reaction to the bot's last message in the chat (else the user's last one), to an explicit MessageRef, or { to?, removed: true } to retract it; reaches bot.on('reaction') and the 'reaction' hooks
pressButton(id | title | index)presses a native button, list row or card button of the last interactive message the bot sent; the bot receives what a real press produces (a 'buttons' message whose body is the id, ctx.interaction.data). Throws when nothing interactive was sent, the target is unknown or it is a URL button. With new MockProvider({ buttons: false }) menus are numbered text: use chat.send('1')
sendInteraction(data, { kind?, id? })a raw interaction (ctx.interaction.data), e.g. { kind: 'command' }
expectReply(text | regexp, timeoutMs?)resolves with the first matching reply (already sent or arriving before the timeout, 1 s by default)
expectNoReply({ timeout? } | ms)resolves when no unconsumed reply exists nor arrives within the window (300 ms by default); rejects listing the unexpected replies. Consumes nothing
replies() / sent() / lastReply()the texts of every reply; every outbound entry with its full content and ref; the last one
transcript(opts?)the exchange as a golden transcript (see Conversation snapshots)

The helpers throw TestKitError with an actionable message. expectReply and expectNoReply poll with real timers: under vi.useFakeTimers() advance them (vi.advanceTimersByTimeAsync) or leave setTimeout/setInterval unfaked.

You can also drive the mock directly: provider.incoming(text, { from, sender, ... }), provider.incomingMedia(kind, bytes, opts), provider.interaction(data, { kind }) (button and list taps), provider.incomingLocation(location, opts), provider.reaction(emoji, { to }) and provider.call({ id, from, status }) (for CALL triggers). provider.journal keeps inbound messages, interactions and sends (with their ref) in order, bounded by maxJournal (10 000 by default).

provider.acks records every interaction ack. new MockProvider({ interactionsRequireAck: true }) simulates a transport with a hard ack deadline (Discord), where the core acks each interaction on its own; pass provider.interaction(data, { respondBy }) to set the deadline.

editMessage, deleteMessage and sendDraft are real methods (recorded in edits, deleted and drafts) that you can override in a subclass. They are exposed according to new MockProvider({ streaming, supports }): edit and delete when streaming is not 'none', drafts with 'draft'. A disabled one reads undefined, so the bot treats it as unsupported; pass supports: { edit: true } to enable one, or supports: { edit: false } to simulate a transport without it (this also hides a subclass override).

Several users and groups ​

ts
const { bot, chat, dm, group } = await createTestBot()

const ana = dm('ana@s.whatsapp.net', { displayName: 'Ana' })      // another DM
const team = group('team@g.us', { as: 'ana@s.whatsapp.net' })     // a group, driven by Ana
const beto = team.as('beto@s.whatsapp.net', { displayName: 'Beto' })  // same group, another participant

await team.send('hi'); await beto.send('hi')
await team.expectReply('Your name?'); await beto.expectReply('Your name?')

Each view carries chatId, senderId, isGroup and displayName. Views of the same chat share one reply cursor (group replies are not per sender), so participants read the chat's replies in order, while conversations stay per participant (conversationScope: 'participant'). On a DM, chat.as(userId) is another DM. provider.journal holds the events every view emitted, ready for assertStableIdentity.

Conversation snapshots ​

ts
expect(chat.transcript()).toMatchSnapshot()

chat.transcript({ as: 'text' })
// user@s.whatsapp.net> hi
// bot< Your name?

chat.transcript({ name?, ids?, timestamps?, scope?, as? }) returns a golden transcript with the shape recordTranscript produces: it parses, redacts (redactTranscript) and replays (assertTranscript) unchanged. Ids and t offsets are dropped by default so snapshots stay stable; scope: 'all' interleaves every chat the mock saw and as: 'text' renders one line per turn. Reactions are not transcript turns.

Vitest matchers ​

ts
// vitest.setup.ts (a `setupFiles` entry) or at the top of a test file
import { expect } from 'vitest'
import { botMatchers } from '@botmesh/core/testing/vitest'
expect.extend(botMatchers)

expect(chat).toHaveReplied('Your name?')               // string includes / RegExp
expect(chat).toHaveRepliedMatching((text, content) => content.kind === 'image')
expect(provider).toHaveRepliedTimes(2)                 // also provider.outbox or a string[]

@botmesh/core/testing/vitest exports the matchers and augments vitest's Matchers type (.not works). vitest is an optional peer dependency: nothing is imported from it at runtime. The matchers are synchronous: wait with expectReply, then assert.

MockProvider always uses a stable from. To test identity changes and hostile delivery, use the chaos kit below.

Chaos kit: adversarial delivery ​

ChaosProvider wraps any IProvider (usually MockProvider) and delivers its traffic adversarially: duplicates, reordering, latency, failed sends, disconnects and identity aliases. It is deterministic for a given seed.

ts
import { createTestBot } from '@botmesh/core/testing'

const { bot, provider, chaos } = await createTestBot({}, {
  chaos: {
    seed: 7,
    duplicates: 0.3,                        // or { probability, copies, delayMs }
    reorder: 3,                             // or { window, maxHoldMs, strategy: 'shuffle' | 'reverse' }
    latency: { min: 0, max: 5 },
    sendFailures: { attempts: [2], errors: ['rate-limited'], retryAfterMs: 500 },
    disconnects: { afterInbound: [5], downtimeMs: 20, replayOnReconnect: 2 },
    aliases: { map: { '573001@s.whatsapp.net': ['999@lid'] }, strategy: 'cycle' },
  },
})
bot.when('hi', async (ctx) => await ctx.reply('👋'))
provider.incoming('hi', { from: 'u1' })   // keep driving the mock
await chaos.settle()                        // wait for pending deliveries (real timers)

With any provider: const chaos = withChaos(myProvider, { seed: 1, duplicates: 1 }); new Bot({ provider: chaos }).

OptionWhat it simulates
duplicatesredelivery (webhook retries). With delayMs: 0 (default) the copy arrives in the same tick, the worst case
reordershuffles events inside a window, in arrival order
latency / sendLatencyfixed delay or { min, max } range, in ms
sendFailurestransient failures with typed errors: 'rate-limited', 'unreachable', 'payload-too-large', 'outside-window', 'unsupported', 'disconnected' or your own factory. Cycled in order; pick them by attempts (1-based), probability or cap them with maxConsecutive. A failed send does not reach outbox
disconnectsautomatic drops (closed → connecting → ready). While down, inbound is held and sends fail with ChaosDisconnectedError. replayOnReconnect redelivers the last N messages, like an offline sync
aliasesthe same person under several wire ids (LID/PN). Without resolve it simulates a provider that leaks aliases and breaks the identity contract; with resolve it tests your resolver
kindsevent kinds affected. Default ['message', 'interaction']; connection events always pass straight through

Manual controls: chaos.disconnect({ reason, downtimeMs }) (without downtimeMs it stays down until chaos.reconnect()), chaos.replay(n) (an explicit webhook retry), chaos.flush() and chaos.settle(). For assertions: chaos.log (what was injected) and chaos.delivered (what reached the bot). For exact timing use vi.useFakeTimers() and vi.advanceTimersByTimeAsync().

Since inbound dedupe is on by default, a bot under duplicates and replay should still answer each message once.

Identity contract for providers ​

Every provider must emit the same senderId for the same person, whatever alias the transport uses (see the identity contract on IProvider). These helpers check a list of emitted events:

ts
import { assertStableIdentity, checkIdentityContract, recordEvents } from '@botmesh/core/testing'
// e.g. Baileys' mapper (no semver): import { IdentityStore, toInbound } from '@botmesh/baileys/internal'

const events = [toInbound(a, identity), toInbound(b, identity), toInbound(c, identity)]
assertStableIdentity(events, { andres: { events: [0, 1, 2], senderId: PN, chatId: PN, kind: 'dm' } })

checkIdentityContract(events, { andres: [0, 1, 2] })   // → IdentityViolation[] instead of throwing

const rec = recordEvents(provider)                      // capture what a real provider emits
// ... drive the provider ...
assertStableIdentity(rec.events, { andres: [0, 1] })
rec.stop()

What it checks:

  • ids are non-empty and do not look like undefined/null/NaN/[object Object];
  • from/chatId/chat.id, sender/senderId/senderInfo.id and ref.chatId agree;
  • ChatKind is valid and consistent with isGroup/isBroadcast, and a chat never changes kind;
  • per person: one senderId, one DM chatId, and the expected ids/kind;
  • two different people never share a senderId.

Options: requireRefChatId, rejectSuspiciousIds, distinctHumans. assertStableIdentity throws an IdentityContractError with violations. A real example lives in packages/baileys-provider/tests/identity-contract.test.ts.

Provider contracts ​

Three more checks keep every channel consistent (see the cross-channel contract). Each built-in provider runs them in its tests/channel-contract.test.ts.

ts
import { assertCapabilityContract, assertInboundContract, assertPresenceWhileDisconnected, recordEvents } from '@botmesh/core/testing'

// Inbound shape: epoch-ms timestamps (never seconds, never 0), string body, mentions array.
const rec = recordEvents(provider)
await provider.ingest?.(webhookBody, headers)   // e.g. a webhook provider fed a recorded payload
assertInboundContract(rec.events)

// Capabilities agree with the methods: typing() ⇔ capabilities.typing,
// markRead() ⇔ readReceipts, editMessage() ⇔ edit, valid text limits.
assertCapabilityContract(provider)

// Presence while disconnected: on a provider that is not started (and whose transport
// throws if contacted), typing() and markRead() resolve without reaching it.
await assertPresenceWhileDisconnected(new MyProvider(config), { chatId: '123' })

checkInboundContract(events, { now?, maxFutureSkewMs?, minTimestamp? }) returns the violations (timestamp-missing, timestamp-unit, timestamp-future, respond-by, body, mentions, message-type); assertInboundContract throws an InboundContractError. checkCapabilityContract / assertCapabilityContract do the same for capabilities (CapabilityContractError). MockProvider passes both: it emits epoch ms, and its typing/readReceipts flags follow whether a typing()/markRead() method exists (a subclass or a test that adds one gets the flag). checkPresenceWhileDisconnected / assertPresenceWhileDisconnected report the rule presence-disconnected when typing() or markRead() rejects while not connected.

Golden transcripts ​

To lock down whole conversations, record one (recordTranscript) or read it from the store log (transcriptFromStore), redact it, commit it as JSON and replay it in a test with assertTranscript: any changed, missing or extra reply fails with an expected-vs-actual diff. The same replay can gate a deployment. See Golden transcripts.

ts
import { assertTranscript, parseTranscript } from '@botmesh/core/testing'

await assertTranscript(parseTranscript(readFileSync('tests/golden/checkout.json', 'utf8')), buildBot)

Static checks ​

eslint-plugin-botmesh catches v1 API leftovers, a blocking runtime.enter(), async plugin install(), empty triggers, waits without a timeout and per-user state in module variables before the code runs.
